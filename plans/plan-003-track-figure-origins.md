# Plan 003: Track Figure Origins and Preserve Valid Zeroes

## Executor instructions

Implement after Plans 001 and 002. This is a data-model migration: protect existing local user data, add exhaustive tests, and do not infer provenance more confidently than the stored records allow. A numeric zero is a valid value, not a missing-value sentinel.

## Why this change

The current recalculation path uses zero as a proxy for “not supplied.” For example, fields are conditionally replaced with logic shaped like:

```ts
fy.medicareLevy || engine.medicareLevy
```

That makes these states indistinguishable:

- The document explicitly reported `$0`.
- The user manually entered `$0`.
- The field was never supplied.
- The engine previously derived `$0`.

As a result, importing or editing one figure can overwrite unrelated document-authoritative or manually corrected values.

Conventions to preserve:

- `AustralianFinancialYear` is the persisted aggregate model.
- `manualFigures.ts` is the controlled path for user-edited headline figures.
- Parsed documents retain their metadata in the year record.
- Existing localStorage data must remain loadable.

## Scope

In scope:

- Add explicit per-field origin metadata.
- Mark parsed, manual, and derived values at their write boundaries.
- Recalculate only values that are absent or derived.
- Migrate legacy saved years conservatively.
- Preserve explicit zeroes from documents and manual edits.

Out of scope:

- Year-specific tax-rule changes; Plan 004.
- Redesigning all nested document line-item provenance.
- Cloud sync or server-side migration.
- Removing existing user records.

## Implementation steps

### 1. Define the origin model in the shared tax types

In `src/types/tax.ts`, define a shared field-key union for the editable/derived headline figures and:

```ts
export type FigureOrigin = 'document' | 'manual' | 'derived';
```

Add an optional, serialisable map to `AustralianFinancialYear`, for example:

```ts
figureOrigins?: Partial<Record<FinancialFigureKey, FigureOrigin>>;
```

Avoid a circular import from `manualFigures.ts`; move the existing editable-field union into `types/tax.ts` or define the canonical key type there and import it everywhere else.

Keep the property optional so pre-migration stored JSON still deserialises.

Verify:

```bash
npm run build
```

Expected: all call sites compile against one canonical field-key type.

### 2. Initialise new workspaces explicitly

Update `src/data/blankFinancialYear.ts` to initialise `figureOrigins` without labelling default zeroes as user-provided values. An empty map is preferable to marking every zero as derived unless the constructor actually runs the engine.

Add a test that a new blank year is distinguishable from a year where the user explicitly entered zero.

Verify:

```bash
npm run test:run -- src/data/blankFinancialYear.test.ts
```

Expected: blank fields have no authoritative origin.

### 3. Mark origin at each write boundary

Update:

- `src/lib/applyParsedDocument.ts`: every accepted parsed headline field gets origin `document`.
- `src/lib/manualFigures.ts`: every explicit user edit, including zero, gets origin `manual`.
- Calculation/recalculation helpers: every value generated by the engine gets origin `derived`.

Clone origin maps when returning updated state; do not mutate prior React state. Preserve manual/document origin when a write path does not touch that field.

Add tests covering:

- Parsed `$0` Medicare levy remains document-origin.
- Manually entered `$0` HELP repayment remains manual-origin.
- A calculated assessment becomes derived-origin.
- Editing gross income does not silently reclassify a manual deduction.

Verify:

```bash
npm run test:run -- src/lib/applyParsedDocument.test.ts src/lib/manualFigures.test.ts
```

Expected: origins and values change together.

### 4. Make recalculation origin-aware

Replace truthy/falsy fallbacks with explicit policy:

- `manual` and `document` values remain authoritative unless that exact field is explicitly replaced by a new manual/document action.
- `derived` or origin-less derivable fields may be recalculated when upstream inputs change.
- A derived downstream field is invalidated/recomputed when a relevant upstream figure changes.
- Exact zero follows the same policy as every other number.

Centralise this decision in a small helper rather than duplicating `origin === ...` checks across application and manual-edit flows.

Document the dependency graph for at least:

- gross income and deductions → taxable income
- taxable income/year → income tax, Medicare, HELP
- tax and credits → assessment result
- gross income and obligations → effective tax rate

Verify:

```bash
npm run test:run -- src/lib/applyParsedDocument.test.ts src/lib/manualFigures.test.ts
```

Expected: upstream edits recompute derived descendants while preserving authoritative descendants.

### 5. Migrate existing localStorage records conservatively

In `src/storage/db.ts`, add a versioned normalisation/migration step used by every load/import path.

Migration policy:

- Existing `manualOverrides` map to `manual` origins.
- Values directly evidenced by retained parsed document fields map to `document`.
- Values the old engine clearly produced may map to `derived` only when this can be established safely.
- Ambiguous non-zero legacy values should be preserved and treated as authoritative, not recalculated away.
- Ambiguous zeroes should remain numerically unchanged; do not invent a manual claim.

Keep the migration idempotent. Never delete documents, collections, or financial years. Add fixture tests for old JSON with and without `manualOverrides`, repeated migration, and export/import round trips.

Verify:

```bash
npm run test:run -- src/storage/db.test.ts
```

Expected: legacy fixtures retain all values and repeated loads produce identical data.

### 6. Run complete verification

```bash
npm run lint
npm run test:run
npm run build
```

Manually import a document, set an authoritative field to zero, change gross income, reload the app, and confirm the zero and its origin survive.

## Done criteria

- Missing and zero are no longer conflated.
- Every new parsed/manual/derived headline write records its origin.
- Recalculation preserves document and manual values.
- Legacy records load without loss and migration is idempotent.
- All tests, lint, build, and the manual reload scenario pass.

## STOP conditions

Stop and report before proceeding if:

- A migration cannot preserve ambiguous legacy values without changing their meaning.
- Origin tracking requires deleting or rewriting raw parsed documents.
- Two current write paths disagree on which field is authoritative and there is no product rule to resolve the conflict.
- Storage is modified outside the existing local workspace boundary.

## Maintenance notes

Add every new headline financial figure to the canonical key union, origin-aware dependency graph, migration normaliser, and tests. Treat origin metadata as part of the persisted compatibility contract.
